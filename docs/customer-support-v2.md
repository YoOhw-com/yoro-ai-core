# Customer Support v2 Core

Core renders customer support and reads current local WordPress/WooCommerce facts. The API owns semantic decisions, settings/identity authority and shared-credit settlement. There is no Core keyword/language intent router, background source index, order writer or new wallet.

The existing Chat Support Settings URL contains five tabs: Overview, Answer sources, Orders & verification, Appearance, Data & usage. Nonce, manage_options, yoro_manage_connection and signed API actor remain mandatory. Public posts/pages can be classified/mapped to current public products. Source selection is explicit; private/password/deleted/unselected content is excluded. New commerce/private flags default off. Saves submit the rendered revision so API rejects stale forms. Appearance offers name/welcome/launcher/accent/position/starters, with a contrast fallback. Preview uses sample data and sends no mail/AI request.

The frontend separates the composer from email/code, product/destination/coupon, rate and order forms. All calls use same-origin no-store transport, session-cookie CSRF and server-held credentials. Transcript/context are memory-only. Two explicit retries retain the original UUID/input. Static order selection only displays details and an explicit Ask action; only a real pending customer question resumes automatically. Forms/previews do not create AI turns; an explicit explanation/resumed customer question can. Private cards/messages clear on end-private, expiry or current verification/readiness loss. Public product cards project at most four cited current native products (price/currency/stock/SKU/options), never model-written amounts or links. Source links are current same-site HTTPS. Desktop is modeless; mobile traps focus while open, Escape closes, and focus returns to launcher.

Protocol 2 is required for new controls; cached protocol-1 settings retain public support only. Encrypted context tokens contain inputs, not permissions or cached facts. Every read reauthorizes at API and recomputes native/current facts; session/credential/revision/expiry changes invalidate tokens. Selected facts are compared before complete/expose/replay. Opaque order references bind current verified email/access/session and current order ownership. Core never exposes API site keys/session credentials or treats a browser-provided email/order ID as authorization.

Native estimates use temporary Woo cart/customer/session objects, guest identity, native totals/tax/shipping/discount/gateway eligibility and a fail-closed supported integration profile. Original live objects/current user are restored. There are no cart/session/order/coupon/stock/payment mutations; outbound HTTP is denied. Native BACS/Cheque/COD are supported initially. Unknown Woo callbacks/gateways and uncharacterized third-party/multi-package plugins require checkout instead. Estimates are recalculated at checkout; recorded tracking does not imply live carrier data/ETA. Customer email restrictions require API-verified email.

Run existing standalone PHP facts/security/session tests, `node --check` for both assets, and `node tests/customer-support/widget-protocol-test.js` for the unit DOM transport test. The latter is not browser rendering or visual acceptance. Run real disposable WP/Woo/MySQL engines with:

The selected source-test profile is WordPress 7.1, WooCommerce 11.0.1, PHP 8.5 and owned MySQL 8.4. The native callback profile adds nine exact hook/priority/arity/file/callable tuples for Woo 11.0.1 while retaining the historical 11.2.1 table. Tests characterize 13 actually loaded WordPress helper bindings (including the native no-stock sanitizer); the separate low-stock admin guard fixture is removed before native REST quoting. Native quote/effect assertions do not depend on that fixture. The runner's `wire` suite accepts an explicit `--wire-fixture` JSON with owned API/Core source roots, the locked dependency root and a boolean Woo mode. It runs fresh native Woo-off/on public facts through actual API validation/settlement, then the actual API settings/completed-answer DTOs through actual Core settings/transport/turn rendering. Exact baseline/current source snapshots test both backward directions. HTTP/model responses and the Core session cookie are synthetic; this is source conformance, not installed runtime authentication or provider semantics. Unknown fields, foreign hosts, unselected source IDs and forged citations remain negative tests.

The runner copies code only, excludes site config/uploads/data, initializes socket-only networking-disabled MySQL, seeds synthetic fixtures and removes its owned DB/copies. Native SQL tracing rejects any estimate write to commerce/session tables. Tests cover native sums/taxes/rates/coupons/COD, variations/visibility, encrypted order references/ownership and current API-authorized context revalidation. They do not install on yoplay8 or prove actual model understanding, inbox delivery or production-plugin compatibility.

`php tests/customer-support/render-widget.php` and `php tests/customer-support/render-settings.php` emit standalone source fixtures with synthetic transport/sample data. Human can open these locally. Browser screenshot/keyboard evidence is a separate required step; source generation/unit DOM assertions do not replace it. An owned loopback server may serve these source fixtures under the current Contract. Actual browser interaction with synthetic transport proves that fixture layer only; installed native coupling, real inbox delivery and Human visual acknowledgement remain separate evidence.

The approved G049 source/CI gate requires final exact API/Core identities, tests/findings/remaining evidence and fresh independent cumulative review before push/hosted checks. Runtime installation, deployment, merge and governance adoption retain their own Human gates. Exactly one shared credit per completed AI answer remains unchanged; static controls/previews cost zero and no site quota is introduced. Source-test evidence leaves actual provider, real inbox, installed runtime and Human visual acceptance pending.

### Appearance defaults and local preview

The default assistant name is `YoRo`, with the existing YoRo accent `#2b3a20`. The native color picker and `#RRGGBB` text field stay synchronized; incomplete text remains invalid without changing the last valid preview. Saved custom colors are retained. Both preview and storefront use the YoRo fallback when white text would not meet 4.5:1 contrast.

The optional `appearance.icon` is limited to `yoro-animated`, `yoro-static`, or `chat`. The default reuses the bundled three-cycle SVG and freezes after its third pass. Reduced motion selects the static asset and never restarts animation on this page. Load failures fall back to the bundled static icon, then a fixed chat bubble. These choices apply to the launcher and header, with no uploads, custom URLs or icon service. Older settings without an icon use the default; partial settings updates preserve saved appearance. Preview sends no AI or verification email. Source fixtures embed the approved bundled assets and are not browser acceptance evidence.
