# Task routing

Every task receives exactly one primary class plus zero or more risk flags from `manifests/routing.yaml`. `repository adoption` is the exclusive class for installing, updating, checking, or rolling back the governance package in one component; it is not ordinary `documentation/governance`. Routing determines discovery depth, agent sequence, capability tier, gates, reviewers, recovery evidence, approval points, prohibited behavior, and stop conditions.

The coordinator must stop before application writes when classification is ambiguous, a required specialist is unavailable, a requested repository is outside the approved write scope, or contract/security/recovery ownership is unknown. Lower-capability substitution is forbidden for required architecture, security, contract, or release review.

Selectors, write-scope policies, contextual profiles, and owner requirements are defined in `manifests/routing-selectors.yaml`; aliases are never executable agent names. The resolver normalizes component order, expands explorers and conditional reviewers, applies risk gates/reviews/approvals/stops, validates capability-tier availability, and verifies every concrete agent file. Known contextual subtypes receive a matching profile; other supported combinations use the class policy and remain scope-bounded. Unknown selectors, mismatched profiles, unavailable tiers, or widened scope fail closed. Representative [routing fixtures](../../manifests/routing-fixtures.yaml) execute through that resolver and compare actual resolved output with expectations.

Repository write scope has four separate fields. `candidate_write_scope` contains only declared component IDs and never changes because an approval is added or removed. `write_authorization_state` explains whether task-specific approvals and preconditions passed. `effective_write_scope` is empty until those requirements pass, and the compatibility field `write_scope` is exactly equal to it. `artifact_write_scope` contains non-repository outputs such as `release_evidence` and is never mixed into repository scope.

Repository adoption additionally requires exactly one component-scoped authority bound to the target component, the operation (`install`, `update`, `check`, or `rollback`), and the exact target baseline SHA. It also requires an observed environment/UI writable boundary equal to that component. Changing any bound field invalidates the authority. Preview, managed diff, drift checks, post-install validation, independent review, and rollback evidence are mandatory. Governance adoption never grants permission to change application/runtime paths and never implies product or runtime readiness.

Unassigned global role metadata does not block unrelated ordinary work. An unresolved assignment blocks only when the concrete resolved route requires that protected approval. A blocked approval leaves effective repository scope empty; safe discovery may continue without protected writes. Approval resolution never broadens the candidate repository set.
